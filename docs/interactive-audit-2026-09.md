# Interactive Correctness Audit — September 2026

Scope: audit #2 of the broader audit menu. Every interactive calculator on the site — the JS behind sliders/inputs that computes a physics quantity — checked for formula correctness, unit consistency, and whether the displayed formula matches what the code actually computes. This is distinct from the earlier science-content audit (which checked whether cited *literature values* were current) and from `tests/formula_regression.py` (which guards ~11 specific conventions already known to be sensitive). This audit went looking for what neither of those covers: wrong textbook formula, missing/extra factors of 2 or 2π, unit mismatches, and dead or misleading code.

Method: read the `<script>` section of every calculator-bearing page (20 pages) plus `js/main.js`, checked each formula against the standard reference for that topic (Foot's *Atomic Physics*, Metcalf & van der Straten, Grimm/Weidemüller, Steck's alkali data notes, Balanis's *Antenna Theory*, Magesan et al.'s randomized-benchmarking conventions), and cross-checked several against known numeric benchmarks (Rb-87 static polarizability ≈319 a.u., Rb-87 Isat = 1.669 mW/cm²).

## Fixed

**`pages/lab-techniques.html` — loop-antenna radiation resistance was 4× too small.** The formula (both in the JS `calcAntenna()` and in the displayed KaTeX formula box — they agreed with each other, both wrong the same way) used `20π²(2πA/λ²)²`. The standard small-loop formula (Balanis) is `20π²(4πA/λ²)²`, equivalently `320π⁴(A/λ²)²` — the well-known "31,171(A/λ²)²Ω" result. Verified by independent derivation and by numeric substitution: for a 10 cm loop at 100 MHz, the correct R_rad is ≈23.7 mΩ; the old code gave ≈5.9 mΩ. Fixed the `4πA` term in both the JS and the KaTeX display. This feeds the loop-antenna calculator used for RF near-field coil design (e.g. driving hyperfine transitions), so a 4× underestimate of radiated power/Q was a real bug worth fixing, not a rounding quirk.

**`pages/rb-explorer.html` — dead code removed.** `rbDecay()` computed an unused, convoluted intermediate expression for `p` immediately before overwriting it with the correct, actually-used expression (`p = 1-2·r_C` for 1-qubit, `p = 1-(4/3)·r_C` for 2-qubit — the standard depolarizing-parameter/error-per-Clifford relation, Magesan et al. convention). The dead line computed nothing wrong, it was just never used — removed for clarity, replaced with a one-line comment stating the same relation the (correct) live code already implements.

## Checked, no issue found

Everything else checked out: `mot-designer.html` (Doppler/MOT theory, Foot Ch. 9), `tof-calculator.html` (ballistic expansion, PSD threshold ζ(3/2)=2.612), `tweezer-designer.html` (trap depth, Lamb-Dicke, Grimm/Weidemüller conventions), `imaging-calculator.html` (detection fidelity model), `cavity-qed.html`, `rydberg-calculator.html` (blockade radius, C₆ ~ n*¹¹ scaling, Rydberg-Ritz quantum defects), `fidelity-budget.html` (all 8 error-budget terms match their displayed equations), `dd-playground.html` (numerically-integrated filter-function engine, self-consistent), `laser-locking.html` (PDH error-signal shape), `cooling-simulator.html` (molasses force/Doppler temperature), `vacuum-systems.html` (ideal gas law, mean free path, pump-down time constant), `zernike.html` (radial-polynomial recursion, OSA/ANSI normalization), `polarimetry.html` (Mueller-matrix rotating-polarimeter formulas, verified algebraically), `release-recapture.html` (polarizability sum rule — numerically matches Rb-87's known ≈319 a.u.), `remote-entanglement.html` (collection efficiency, Purcell factor, two-photon heralding probability), `lab-calculators.html` (~20 mini-calculators spot-checked, including a correct Clebsch-Gordan/Racah implementation and correct EOM-sideband PDH-optimum β≈1.08), `laser-planner.html` (reference lookup, no live computation, low risk), and `absorption-imaging.html` (its atom-number calculator deliberately uses the unsaturated cross section for the shot-noise-floor sensitivity estimate, and separately, correctly flags saturation bias via a live badge plus the saturation-corrected OD formula shown right below — re-read closely and this is intentional, transparent design, not an inconsistency; no change made). `js/main.js` has no physics in it — UI/UX infrastructure only, so no shared-helper risk there.
