# Design & Visual Consistency Audit — Re-check, September 2026

Scope: this is a re-run of audit #3 from the original menu (`docs/design-audit-2026-09.md`, September 8), which is one of four "oldest, never redone" audits alongside cross-page-consistency, interactive-correctness, and content-flow. Rather than re-litigate that report's settled and still-open items, this pass went looking for what nine days of other audits' edits (accessibility, navigation, performance, technical, link) might have missed or introduced, plus a systematic scan for the exact bug *class* the original audit's headline fix (`--r-md` referenced but never defined) belongs to: CSS custom properties that are used somewhere but never defined anywhere, which fail silently (no error, just wrong/missing styling) rather than loudly.

Method: (1) wrote a small script cross-referencing every `var(--x)` usage across all 28 tool pages, `home.html`, `404.html`, `index.html`, and `css/styles.css` against every `--x:` *definition* in those same files, to find the `--r-md`-shaped bugs the original audit didn't get to when it stopped after finding the first one; (2) grepped for leftover literal old-palette hex/rgba values (`#22d3ee`, `#c084fc`, `34,211,238`) site-wide to check whether the two pages the original audit approved remapping (`vacuum-systems.html`, `rb-explorer.html`) were fully migrated or only partially; (3) spot-checked whether the original report's still-open items (theme default, Chart.js grid-line theme-awareness, `prefers-reduced-motion`) have changed status since.

## Fixed

**`var(--mono)` was used in 104 places across 12 pages plus `css/styles.css` itself, but `--mono` is never defined anywhere in the codebase** — only `--font-mono` (`'JetBrains Mono', 'Fira Code', 'Courier New', monospace`) exists. Every one of these 104 rules was silently falling back to the surrounding body font (serif in light "Lab Notebook" mode, sans-serif in dark mode) instead of rendering in monospace — this is the same failure shape as the original audit's `--r-md` bug (an alias that was apparently meant to exist but never got added to the token system), just far more widespread. Affected: `css/styles.css` (3 shared rules — `.eq-mini`, a badge label, and a stat value), `cooling-simulator.html` (5), `dd-playground.html` (4), `fidelity-budget.html` (9), `imaging-calculator.html` (8), `laser-locking.html` (4), `learn-quantum.html` (23), `mot-designer.html` (6), `rb-explorer.html` (7), `release-recapture.html` (8), `rydberg-calculator.html` (9), `tof-calculator.html` (6), `zernike.html` (12). Replaced every occurrence with `var(--font-mono)`. This mostly affects small numeric readouts, formula labels, and mono-styled data values — visually minor per-instance, but consistent and site-wide, so worth fixing as one batch.

**`var(--sp-7)` was used in 13 pages (mostly a `.route-panel`/section-heading top margin) but `--sp-7` was missing from the spacing scale** in `css/styles.css`, which otherwise runs `--sp-1` through `--sp-24` on an exact `value = N × 0.25rem` formula with no other gaps (`--sp-6: 1.5rem`, jumps straight to `--sp-8: 2rem`). Added `--sp-7: 1.75rem;` in the obvious slot between them, consistent with the established formula — a one-line fix in the shared stylesheet rather than touching 13 files individually.

**`rb-explorer.html`'s Clifford-group table's first column used `font-family: var(--font-body, Inter, sans-serif)`** — `--font-body` doesn't exist anywhere either, so (unlike the two bugs above) this one had its own inline fallback and didn't visibly break, but it meant this one table column was permanently stuck in Inter/sans-serif in *both* themes, while the rest of the page's body text correctly switches serif/sans-serif with the light/dark toggle via the real `var(--font-sans)`. Replaced with `var(--font-sans)` so this column tracks the theme like everything else on the page.

**`vacuum-systems.html`'s cyan→ink-blue remap (approved and applied in the original design audit) was incomplete in 3 spots** where a single visual element had its variable-driven half updated but a hardcoded literal copy of the old cyan left in the other half, so the element showed two disagreeing colors: the pressure-slider thumb's fill was `var(--vac)` (now blue) with a cyan `box-shadow` glow; the history-timeline dot had the identical fill/glow mismatch; and the pump-range badge's background was a hardcoded cyan tint while its own text and border already read blue. Fixed all three to one consistent color. Left the page's two decorative SVG equipment-diagram illustrations untouched — those use cyan as one of five deliberately-different hues distinguishing chamber/ion-pump/NEG/turbo/rough-pump in a technical diagram legend, not as the page's singular identity accent, so recoloring just "chamber" there would be a different (and unrequested) kind of change, not a like-for-like completion of the approved fix.

All fixes above are text/value substitutions with no structural changes. `css/styles.css` changed, so its cache-busting `?v=` was bumped from 20 to 21 across all 30 HTML files (`sed` across `pages/*.html home.html 404.html index.html`) and grep-verified — no file still references `v=20`. Tag-balance (div/ul/li/tr/td/section/table/span) was checked on every HTML file touched and came back balanced. `tests/formula_regression.py` was re-run after each batch and stayed 11/11 throughout.

## Flagged, not changed — needs your call

- **`rb-explorer.html`'s Chart.js decay curves still use the pre-remap purple (`#c084fc`) for one of two series in each of its two charts** (1Q vs. 2Q RB decay; reference vs. interleaved RB decay), even though the page's own chrome accent (`--accent`, used for buttons/borders/tab-highlights) was already correctly remapped to ink-blue. I initially suspected this was the same kind of incomplete remap as `vacuum-systems.html`'s, but on inspection it isn't a like-for-like case: each chart pairs the purple series against a *different* second color (`#60a5fa` light blue, `#34d399` green) specifically so the two curves stay visually distinguishable. Recoloring the purple series to match the page's now-blue chrome would put two data series in similar blue hues on the same chart, hurting readability rather than fixing an inconsistency. Left as-is — but flagging because it's a genuine judgment call (is a still-purple chart on an otherwise-blue page a bug or fine), not something I felt right deciding unilaterally.
- **`home.html`'s tools-grid card for Randomized Benchmarking (`QC 05`) is the only one of 25 category-colored cards not using one of the three ink hex values** — it's still `#c084fc`, matching what `rb-explorer.html`'s old `--accent` used to be before the remap (every other card is exactly `#a13c1c`/`#2c4a63`/`#3f5d3f`, no other outliers, except `dd-playground`'s card at `#4ade80` which *does* still match that page's own, never-flagged, still-purple/green `--accent` — so "card color tracks the page's own accent" does appear to be the actual convention here). That makes rb-explorer's card look like a straightforward miss from the earlier remap by that same logic — except its still-purple Chart.js curves are also the single most visually memorable thing about the page, so the purple card could equally be read as intentionally keeping visual continuity with that chart. I didn't want to guess on a home-page, every-visitor-facing color with a plausible case either way — flagging for a decision rather than picking one.
- **Both of the original design audit's two big open items are still unresolved, unchanged since 2026-09-08** (checked, not re-litigated, no new evidence to act on): the site still defaults every new visitor to the dark theme (`getStoredTheme()` in `main.js` returns `'dark'` unless `localStorage` explicitly says `'light'`) while `styles.css`'s own comment still says light "Lab Notebook" is supposed to be the default; and the ~150 hardcoded dark-theme-tuned Chart.js grid/axis colors across ~15 pages are still not theme-aware. Not touched this pass — these are exactly the kind of "changes every visitor's default experience" decisions that need your call, not mine.

None of these were part of the original audit's approved remap scope, and recoloring any of them would be a new, separate judgment call, not a mechanical completion — left untouched.
