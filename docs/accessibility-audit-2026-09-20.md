# Accessibility Audit — Re-check, September 2026

Scope: this is a re-run of audit #8 from the original menu (`docs/accessibility-audit-2026-09.md`, September 9), the least-recently-touched of the eight original audits (accessibility and navigation/IA were both dated September 9, but accessibility's file timestamp is the earlier of the two; performance was September 11). Eleven days and five other audit passes (link 09-16, technical 09-16, design 09-17, cross-page-consistency 09-18, content-flow 09-19) had touched nearly every HTML file since the original accessibility pass — every page's mtime moved except `decoherence-lab.html`/`404.html` (09-17) — so this round's real question was whether any of the original fixes had regressed under that churn, and whether any of that churn introduced new accessibility gaps, rather than re-discovering the same site from scratch.

Method: re-verified every fix from the original report against the current file contents with targeted greps/scripts (main-landmark presence and position, footer-outside-main nesting, `.btn:focus-visible` and `prefers-reduced-motion` CSS, tab-widget ARIA in `initTabs()`, accordion-header tag types, `<th scope>` coverage, decorative-chevron `aria-hidden`, label/`for` pairing with an orphan- and duplicate-id check, range-slider and checkbox accessible names, hand-rolled `role="button"` divs' `tabindex`/`onkeydown`) rather than re-deriving them from a fresh subagent pass — the original report's findings were extensive enough that a diff-against-baseline approach was more reliable than re-scanning blind. Also swept for genuinely new instances of the same issue classes (new images, new dynamically-generated form controls, new clickable divs) that could have been added by the five intervening audits' edits. `tests/formula_regression.py` was run before starting and after every batch (11/11 throughout); tag-balance (div/ul/li/tr/td/th/table/section/main/footer/span/button/select) was checked on every file touched.

## Fixed

- **`pages/decoherence-lab.html` and `pages/laser-planner.html` had no `<footer>` element at all** — every one of the other 26 tool pages plus `home.html` closes with the same `<footer class="footer">…AMO Toolkit · Saumitra Phatak · Purdue University</footer>` block; these two went straight from `</main>` to their `<script>` tags. This wasn't a leftover from the original accessibility pass (both pages already had correct `<main>` landmarks) — it looks like the footer was simply never added when these two pages were built, and no other audit's footer/consistency checks happened to catch it since none of them enumerated "does this page have a footer" as an explicit check. Added the standard footer block to both, using each page's own `<title>` text for the page-name line (`Decoherence Lab` / `Laser System Planner`), matching the sitewide pattern exactly.
- **`pages/zernike.html`'s dynamically-generated "Wavefront Builder" mode rows had zero accessible names on any control** — `renderWFModes()` builds each row's HTML via a template string (`<select>…</select><select id="wfm${idx}">…</select><input type="number" …><button onclick="removeWFMode(${idx})">×</button>`) with no `<label>` anywhere in the template and no static header row above it either (confirmed by reading the surrounding markup — the `.wf-modes` container is just an empty div JS renders into). A screen-reader user adding a Zernike term would hear four unnamed controls per row. This is a different, narrower case than the ~250 static labels the original audit fixed (those all had a real sibling/wrapping `<label>` to hook a `for=` onto; this one has none at all, static or dynamic). Added `aria-label`s built from the same `${idx}` the template already uses ("Radial index n for term N", "Azimuthal index m for term N", "Coefficient for term N", "Remove term N") — mechanical, no visual change, consistent with how the original audit named the 13 label-less range sliders.
- Swept the rest of the codebase for the same "JS template literal builds a bare `<select>`/`<input>`/`<button>` with no label" pattern (grepped every `innerHTML = `\``…`\`` ` block and every `<select`/`<input`/`<button` appearing inside a template literal, sitewide) — zernike's wavefront-mode rows were the only instance; `lab-calculators.html`'s Clebsch–Gordan `buildTable()` (the other JS-generated widget on the site) only emits `<td>`/`<th>` cells, no interactive controls, and was already fully covered by the original audit's `scope` fix.

No shared `css/styles.css` or `js/main.js` edits were needed this round (both fixes were page-local HTML), so no cache-bust version bump applies.

## Flagged, not changed — still open, no new evidence

These three are unchanged from the original report. Re-confirmed current state below; not re-litigating the judgment call itself per this pass's scope (a decision only worth reopening if something material changed):

- **The `<h2>`→`<h4>` heading-hierarchy skip is still present on the same set of pages** (re-scanned programmatically: cooling-simulator, decoherence-lab, dd-playground, fidelity-budget, imaging-calculator, lab-calculators, lab-techniques, laser-cooling, laser-locking (unchanged, still worst-case), laser-planner, learn-quantum, mot-designer, qc-landscape, rb-explorer, release-recapture, remote-entanglement, tof-calculator, vacuum-systems). Root cause (h4 chosen for its smaller default font-size, no reusable "small heading" class) is unchanged. Still your call between bumping to `<h3>` + a new size-preserving class, or something else — flagged, not touched.
- **`--text-muted` still fails WCAG contrast in both themes** (dark `#475569`, light `#8c8066` — same hex values as the original report, confirmed via direct read of the token definitions). One thing worth surfacing since the original report: dark theme is now the site's *default* (a change that landed after this token was originally flagged), so the dark-theme failure (2.41–2.65:1, below even the 3:1 large-text floor) is what most first-time visitors will actually see rather than an opt-in state. Doesn't change the fact that picking a replacement hex is a design call, not a mechanical one — still left as-is — but it does raise the stakes on that call slightly, worth knowing when you get to it.
- **Zero screen-reader fallback for the 94 `<canvas>`/Chart.js graphics** across 26 pages is still true; no `.sr-only` utility class has been added to `css/styles.css` since the original report (checked — still absent). Same "bigger project than one day's budget, needs the utility class as a prerequisite" status as before.
