# Performance Audit — September 2026

Scope: page load performance for a static HTML/CSS/vanilla-JS site with no build step, no bundler, and no server (GitHub Pages) — file weight, render-blocking resource order, CDN resource hints, image loading, CSS/JS duplication, and dead code in the shared JS file. This is the 8th and last item of the original audit menu; all eight are now complete (cross-page consistency, accessibility, and navigation/IA were the three completed in the immediately preceding runs).

Method: delegated a research-only pass to a subagent to measure real file sizes, script-loading order, and resource-hint coverage across all 29 pages, explicitly told not to re-check ground already covered by the six prior audits. Verified the one finding with real correctness risk (making Chart.js non-blocking) by hand-tracing an actual page's script execution order before deciding whether it was safe to apply — it isn't, without a larger restructuring (see below), so it's documented rather than guessed at. Regression suite (11/11) kept green; no file this round needed the tag-balance check since only `<link>` tags (void elements) were added.

## Fixed

- **Zero pages had a `preconnect` hint for `cdn.jsdelivr.net`**, despite 26 of 29 pages loading KaTeX and/or Chart.js from it — every one of those pages was paying a fresh DNS+TLS+TCP handshake to that origin with no early hint, on top of the connection already being opened (via existing `preconnect`) for Google Fonts. Added `<link rel="preconnect" href="https://cdn.jsdelivr.net" crossorigin>` right after the existing font-preconnect pair on all 26 affected pages (25 tool pages + `home.html`; `404.html` doesn't use jsdelivr and was correctly left alone). Zero risk — a resource hint doesn't change script execution order or timing semantics, just lets the browser start the connection earlier while it keeps parsing the rest of `<head>`.

## Flagged, not changed — needs your call (or careful dedicated work, not a safe blanket fix)

- **Chart.js is render-blocking on 19 of 21 pages that use it** — loaded via a synchronous `<script src="…chart.umd.min.js">` in `<head>` with no `defer`/`async`, ahead of the page's own `<style>` block, so it delays first paint. This looks like an easy `defer` fix, but I traced the actual dependency chain on `mot-designer.html` before touching anything and confirmed it would break the page: the trailing inline `<script>` (after `main.js`, itself also non-deferred) calls `new Chart(detuneCtx, …)` at the top level, synchronously, relying on Chart.js having *already* executed by the time the parser gets there. Deferring the Chart.js tag moves its execution to *after* that inline script would already have run and thrown "Chart is not defined." The same synchronous-in-order pattern (Chart.js loads sync → `main.js` loads sync → trailing inline script runs immediately, calling both `renderNav()` and page-specific functions like `new Chart(...)` at the top level) is the shared template used across all 19 affected pages. Making this genuinely non-blocking would mean wrapping each page's chart-creation calls (not the whole trailing script — many of its top-level function declarations are called from `onclick="…"` attributes elsewhere in the page's HTML and would break if hidden inside a listener closure) in a `DOMContentLoaded`/deferred-script boundary, verified per page. That's real, valuable work, but it's page-by-page verification, not a safe one-line sed across 19 files, so I didn't guess at it. Also applies, with lower urgency since it never blocks visible content (already sits at the very end of `<body>`): `js/main.js` itself has no `defer` on any of the 29 pages, for the same reason (the trailing inline script depends on it having already run synchronously).
- **6 functions in `js/main.js` (~271 lines / ~12.7KB, about 12.5% of the file) are defined but never called anywhere** — `initAssumptionBadges`, `initSourceConfidencePanels`, `initLabNotebook`, `initExpertModeToggles`, `initPagePlaybookPanel`, `initReferenceTrailPanel`. Verified each has zero call sites, in `main.js`'s own init block or in any of the 29 pages' inline scripts. Since `main.js` is downloaded and parsed on every single page load, this is genuine shipped-but-unused weight — but it reads like scaffolding for planned-but-not-yet-wired-up features rather than leftover cruft from something removed, so rather than delete functioning (if currently unreachable) code on my own judgment, I'm flagging it for you to confirm: if these are abandoned, they're a clean, low-risk trim; if they're WIP for something you're planning, they should stay.
- **A few small CSS components are duplicated near-verbatim across several pages' local `<style>` blocks** instead of living once in the shared `css/styles.css` — e.g. the `.prop-card`/`.prop-card-label`/`.prop-card-val` stat-card pattern (`mot-designer.html`, `imaging-calculator.html`, `rydberg-calculator.html`, `tof-calculator.html`) and the `.ctrl-panel`/`.field-row` form pattern (`fidelity-budget.html`, `mot-designer.html`, `zernike.html`, plus partial matches elsewhere). Promoting these into `styles.css` (parameterized by a `--page-accent` custom property instead of each page's hardcoded hex) would reduce total bytes transferred site-wide and improve cache reuse across pages, since the shared CSS file is cached once. This is a real refactor across 6-8 page-local style blocks with visual-parity risk if done carelessly, not a one-line fix — flagging rather than attempting it in the same pass as everything else this round.
- **`amo-groups.html` and `paper-syllabus.html` don't load the Google Fonts link at all** (every other page does) — noticed as a side effect of checking font-loading patterns. This isn't a performance problem (it's technically less to load, not more), but it's worth a quick look in case it's an accidental omission rather than a deliberate choice — if unintentional, those two pages likely render in a fallback system font while every sibling page uses Inter/JetBrains Mono. Not touched, since I couldn't tell from the code alone whether it's a bug or a choice.

## Confirmed clean (no action)

- **The two cooling GIFs are already well-optimized**: `assets/cooling/*.gif` are 1.3-1.5MB each, but `laser-cooling.html` already serves them through a `<picture><source srcset=".webp">` with the multi-MB GIF only as a fallback for browsers without WebP support (the WebP versions are ~350-420KB, about 73% smaller), and both `<img>` tags already carry `loading="lazy"`. Nothing to fix here — this looked like an obvious red flag from file size alone until checked in context.
- **No page loads Chart.js without using it.** Checked all 21 pages that load the library — every one calls `new Chart(` at least once. No wasted library downloads.
- **Font loading is already well set up**: `font-display=swap` is present on every Google Fonts link that exists, and `preconnect` to both `fonts.googleapis.com` and `fonts.gstatic.com` was already present everywhere fonts are loaded (this was the existing pattern the new jsdelivr preconnect fix above was modeled on).
- **No raster background images anywhere** — the only two `background-image` CSS rules site-wide are pure gradients, not image files. Only two `<img>` tags exist site-wide (the cooling GIFs, covered above); no other image-loading gaps to find.
- **`main.js`'s organization is solid** apart from the dead-code question above — 46 clearly-named top-level functions, each covering one feature (nav, search, accordions, tabs, scroll-reveal, related-tools, quiz, etc.), matching its documented role as the single shared JS file for a no-build-step site.
- **The two largest pages** (`learn-quantum.html` at 155KB/14 topics, `lab-techniques.html` at 154KB/8 techniques) are large because they're intentionally content-dense single-page references, consistent with the site's established one-page-per-tool philosophy (`docs/site-philosophy.md`) — not bloat, and not something to split without revisiting that philosophy.
